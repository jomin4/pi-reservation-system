# 코레일 운행정보 조사

조사일 2026-09-10 · 대상 **실제 운행 데이터의 모양**

## 목적

> 시드 48만 건을 깔되, **나중에 실제 코레일 운행정보로 갈아끼울 수 있는 구조**인지 확인한다.

`data.md` §7 시드 설계에 앞서 실제 데이터가 어떤 필드를 갖는지 대조한다. 지금 스키마를 더 일반화할지, 아니면 시드 생성기만 그 모양에 맞출지를 가른다.

| 구분 | 표기 |
|---|---|
| 확인 | 공식 데이터 명세 · 보도로 확인 |
| 미확인 | 값 자체는 별도 API 조회 필요 |

---

## 1. 열차번호 체계

| 축 | 내용 | 신뢰도 |
|---|---|---|
| 자릿수 | **3자리** — KTX는 101~899 | 확인 |
| 번호대 | **100번대 = 서울~부산 경부고속선 전용** | 확인 |
| **방향** | **서울 기준 지방행(하행) = 홀수 · 서울행(상행) = 짝수** | 확인 |
| 예 | `KTX 101` = 고속열차 · 경부선 · **부산 방향** | 확인 |

> **번호 하나에 종류·노선·방향이 다 들어 있다.** 우리가 `train_no`를 임의 문자열로 두면 이 정보가 사라진다. 시드 생성기가 규칙을 지키면 **공짜로 현실성을 얻는다.**

---

## 2. 공공데이터 — 열차운행정보 API

**한국철도공사_열차운행정보** — 여객열차 운행계획 및 운행정보

| 필드 | 우리 대응 |
|---|---|
| `운행일자` | **`trip.service_date`** ✅ |
| `열차번호` | **`trip.train_no`** ✅ |
| `출발역코드` · `도착역코드` (`stn_cd`) | `station.code` ⚠️ 형식 다름 |
| `출발역명` · `도착역명` | `station.name` ✅ |
| `열차계획출발일시` | **`trip.depart_at`** ✅ |

> **역 코드 실제 값은 미확인.** 필드명이 `stn_cd`인 것과 코드정보 API로 조회해야 한다는 것만 확인됐다. 실제 값 대조는 실 연동 시점의 과제로 남긴다.

---

## 3. 공공데이터 — 열차정보 (편성)

편성된 열차의 **차량 연결 순서와 객차 종류**를 제공한다.

| 필드 | 뜻 |
|---|---|
| `편성번호` · `열차종` | 어떤 차량인가 |
| **`차량연결순서`** | **호차 순서** |
| **`객차차실종류`** | **일반실 / 특실** |
| `동차여부` · `차종` | |
| `주행거리(km)` · `차량환산량수` | |
| `연결역명` · `해방역명` | 중련 · 분리 운행 |

**핵심** — 편성 정보가 **운행 정보와 분리**돼 있다. 우리 `train` · `seat_layout`과 `trip` · `trip_seat`의 분리와 같은 구조다.

---

## 4. 좌석 수는 편성마다 다르다

| 편성 | 좌석 |
|---|---|
| KTX-1 | **935석** (특실 127 + 일반실 808) |
| KTX-산천 | **363석** |
| 우리 | **800석** — `10 × 20 × 4` (`data.md` §1-B) |

> `seat_layout`이 **`train_id` 기준**이라 편성이 늘어도 스키마가 안 바뀐다. 800석은 808석(특실 제외)을 계산 편의로 맞춘 값이다.

---

## 5. 우리 스키마와 대조 — 확장 준비 상태

| 실제가 가진 것 | 우리 | 판정 |
|---|---|---|
| 편성마다 좌석 수 다름 | `seat_layout`이 `train_id` 기준 | ✅ **이미 확장 가능** |
| 열차가 모든 역에 안 섬 | `trip_stop`이 운행별 정차 목록 | ✅ **이미 유연** |
| 평일/주말 시각표 다름 | `trip`이 `service_date`별 행 | ✅ **시드 생성기 문제** |
| 상·하행 방향 | `line_seq` + `stop_seq`로 파생 | ✅ 저장 불필요 |
| 객차차실종류 (특실/일반) | 없음 — **좌석 등급 폐기** | ⚠️ 의도된 축소 |
| 열차 등급 (KTX/ITX/무궁화) | `train.model` 1종 | ⚠️ 컬럼 추가로 해결 |
| **노선 2개 이상** | `station.line_seq`가 **단일 노선 가정** | ⚠️ `route` 테이블 필요 |
| **운임** | **없음** | ❌ **설계 구멍** |

> **이 조사의 가장 큰 결론** — **확장 대비의 실체는 스키마가 아니라 시드 생성기의 모양이다.**
>
> `seat_layout` · `trip_stop` · `service_date`가 이미 정규화돼 있어서, 실제 데이터를 붙이려면 **생성기를 로더로 바꾸기만** 하면 된다. 지금 스키마를 더 일반화하는 건 **쓰지도 않을 유연성을 사는 것**이다.

---

## 6. 이 조사가 설계에 남긴 것

| 항목 | 결과 |
|---|---|
| **열차번호 홀짝 규칙** | ✅ **채택** — 하행 홀수 · 상행 짝수. 시드 생성기가 지킨다 |
| **`fare` 테이블 신설** | ✅ **채택** — 코레일도 역 쌍 운임표 방식. 테이블 11 → 12개 |
| **애플리케이션 러너로 주입** | ✅ **채택** — 시드가 *값*이 아니라 *규칙*으로 남아야 로더 전환이 싸다 |
| 의미 있는 역 코드 유지 | ✅ `SEO` `DJN` `DDG` `BSN` 유지. 실제 코드는 나중에 `external_code` 컬럼으로 |
| 편성별 좌석 수 | ❌ 지금 대응 불필요 — `seat_layout`이 이미 감당한다 |
| 좌석 등급 (특실) | ❌ **범위 밖** — 동시성·정합성과 무관 |
| 노선 다중화 | ⏸️ **보류** — 필요해지면 `route` · `route_station`으로 분리 |
| **공공데이터 실연동** | ❌ **2026-09-10 미채택** — 아래 참조 |

### 공공데이터를 쓰지 않기로 한 이유

검토는 했다. 세 층위 중 **빌드 타임 수입(CI가 호출 → 폐쇄망이 pull)**이 가장 합리적이라는 결론까지 갔으나 채택하지 않았다.

| 걸림돌 | 내용 |
|---|---|
| **승인 대기** | data.go.kr은 활용신청 후 **승인까지 시간이 걸린다.** 개발 착수를 여기 걸 수 없다 |
| **주는 게 절반** | 시각표는 주지만 **좌석 배치도 운임도 없다.** 48만 행은 어차피 우리가 만든다 |
| 정규화 비용 | 실제 경부선은 정차 패턴이 제각각. **4역 전부 정차하는 편만 거르는** 필터가 따로 필요하다 |

> **이 프로젝트가 증명하려는 건 좌석 동시성이지 데이터 수집이 아니다.** 실제 시각표를 붙여도 `trip_seat` 48만 행과 그 위의 락 전략은 한 글자도 안 바뀐다. **바뀌는 건 `trip` 600행의 출처뿐**이고, 그 대가로 외부 승인 절차가 일정에 들어온다.
>
> 다만 **조사 자체는 값을 했다** — 열차번호 홀짝 규칙과 운임표 방식을 여기서 얻어 시드에 반영했다.

> **`line_seq`가 유일한 시한폭탄이다.** "노선상 순서"라는 이름이 **노선이 하나임을 전제**한다. 노선이 둘이 되는 순간 이 컬럼은 의미를 잃고 `route_station(route_id, station_id, seq)`로 옮겨야 한다. 지금 미리 나누지 않는 이유는 **4역 단일 노선에서 테이블 하나를 더 두는 값이 없기** 때문이다.
