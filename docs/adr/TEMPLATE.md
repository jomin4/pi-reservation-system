## 쓰기 전에 — 이 결정이 ADR 감인가

**세 질문에 전부 "예"여야 쓴다.**

| # | 질문 | 예시 |
|---|---|---|
| ① | **되돌리기가 비싼가?** | 모듈 경계 · 락 전략 · 저장소 선택 |
| ② | **대안을 실제로 저울질했나?** | 두 개 이상을 비교하고 하나를 버렸다 |
| ③ | **6개월 뒤 "왜 이랬지?"를 물을 것 같나?** | 코드만 봐서는 이유가 안 보인다 |

**쓰지 않는 것**

| 안 씀 | 이유 |
|---|---|
| 관례로 정해지는 것 | `camelCase` · 파일 명명 · 들여쓰기 |
| 대안이 없던 것 | "PostgreSQL을 쓴다" (이미 확정된 전제의 결과) |
| 코드를 보면 아는 것 | 함수 분리 · 클래스 이름 |
| **아직 안 정한 것** | ADR은 결정 기록이지 제안서가 아니다 |

> **한 건에 1~2쪽.** 넘기면 아무도 안 읽는다. 길어지면 결정이 두 개 섞인 것이니 나눈다.

## 지켜야 할 규칙

| 규칙 | 내용 |
|---|---|
| **불변** | 한 번 채택된 ADR의 본문은 **고치지 않는다.** 오탈자만 예외 |
| **바뀌면 새 ADR** | 옛 ADR의 `상태`를 `대체됨`으로만 바꾸고, 새 번호로 쓴다 |
| **과거형** | 그 시점의 기록이다. "지금 어떻게 되어 있나"는 설계 문서가 답한다 |
| **충돌 시** | ⚠️ **설계 문서가 이긴다.** ADR은 역사 기록이지 현재 진실이 아니다 |
| 번호 | 4자리 · **재사용하지 않는다** |

### 상태 값

| 값 | 뜻 |
|---|---|
| `채택` | 현재 유효 |
| `대체됨` | 후속 ADR이 뒤집었다. **번호를 반드시 적는다** |
| `폐기` | 전제가 사라져 결정 자체가 무의미해졌다 |
| `소급 작성` | 결정 이후에 기록했다. **각색되었을 수 있음을 인정하는 표시** |
