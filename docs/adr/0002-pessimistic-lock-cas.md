# ADR-0002 — 좌석 선점을 비관적 락 + CAS 가드로 처리한다

| | |
|---|---|
| 상태 | 채택 · **소급 작성** |
| 날짜 | 2026-09-08 |
| 대체 | — |
| 관련 문서 | [data.md §4](../data.md) · [data.md §5](../data.md) |

## 맥락

이 프로젝트가 증명하려는 명제 자체다.

> **N개 요청이 같은 좌석을 동시에 노릴 때 정확히 1건만 성공해야 한다.**

두 겹의 제약이 더 붙어 있었다.

| 제약 | 내용 |
|---|---|
| **원자성** | 최대 6석을 한 덩어리로. **부분 성공이 없다** |
| **잠금 순서** | 두 요청이 같은 좌석 집합을 반대 순서로 잠그면 **데드락** |
| 만료 회수 | TTL 10분 스케줄러가 확정과 부딪힐 수 있다 |

대상은 `trip_seat` **48만 행** 한 테이블뿐이었다.

## 검토한 대안

| 대안 | 장점 | 단점 | 판정 |
|---|---|---|---|
| 낙관적 락만 (`version`) | 락 없음 · 처리량 | **경합 시 재시도 폭주** · 6석 원자성 보장이 복잡 | ❌ |
| **`SELECT … FOR UPDATE`** | 정확 · 표준 | 대기 발생 | ✅ **채택** |
| `FOR UPDATE NOWAIT` | 즉시 실패 | **찰나의 겹침도 실패** — 체감 실패율 과도 | ❌ |
| **`FOR UPDATE SKIP LOCKED`** | 대기 0 | ⚠️ **부분 성공이 생긴다** | ❌ **금지** |
| Redis 분산락 | 빠름 | **좌석의 진실이 두 곳** — 정합성 근거가 흔들린다 | ❌ |

## 결정

> **비관적 락으로 판정하고, 락 밖 경로는 `version` CAS로 막는다.**

```sql
SELECT id, status, hold_id, reservation_id, version
  FROM trip_seat
 WHERE trip_id = ? AND id = ANY(?)
 ORDER BY id                -- ← 이게 없으면 데드락
   FOR UPDATE;
```

| 장치 | 값 | 막는 것 |
|---|---|---|
| `ORDER BY id` | 오름차순 고정 | **데드락** |
| 테이블 순서 | `trip_seat → seat_hold → reservation` | 테이블 간 데드락 |
| `lock_timeout` | **200ms** | 무한 대기 |
| `version` CAS | `WHERE version = ?` | **스케줄러 등 락 밖 판단 경로** |
| 격리 수준 | `READ COMMITTED` | 직렬화 실패 재시도 루프 회피 |

**`SKIP LOCKED`를 금지한 게 이 결정의 핵심이다.** 대기열이나 작업 큐라면 잠긴 행을 건너뛰는 게 정답이지만, **6석을 한 덩어리로 잡아야 하는 여기서는 건너뛰는 순간 규칙이 깨진다** — 4석만 성공한 예약이 생긴다.

## 결과

| 얻은 것 | 잃은 것 |
|---|---|
| **정확히 하나만 성공** — SQL 한 방으로 증명 가능 | 락 대기 · **처리량 상한** |
| 데드락이 구조적으로 불가능 | `lock_timeout` 초과 = `409`가 정상 발생 |
| 락 밖 경로(스케줄러)까지 방어 | **`trip_seat`에 인덱스를 못 늘린다** (`data.md` §8) |

**최종 증거**를 이 결정이 만든다.

```sql
SELECT r.trip_id, rs.car_no, rs.row_no, rs.col_letter, count(*)
  FROM reservation_seat rs JOIN reservation r ON r.id = rs.reservation_id
 WHERE r.status = 'CONFIRMED'
 GROUP BY 1,2,3,4 HAVING count(*) > 1;   -- 기대: 0 rows
```
