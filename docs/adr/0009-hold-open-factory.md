# ADR-0009 — 6석 규칙을 `Hold` 의 정적 팩토리 안에 가둔다

| | |
|---|---|
| 상태 | 채택 |
| 날짜 | 2026-09-17 |
| 대체 | — |
| 관련 문서 | [back.md](../back.md) §2 · [data.md](../data.md) §4·§5 · `api/components/holds.yaml` · ADR-0002 |

## 맥락

`F-04` 의 규칙은 한 줄이다 — **"최대 6석, 전부 성공 또는 전부 실패."** 도메인 코어를 그리는 단계에서 이 한 줄이 두 가지로 쪼개진다는 것이 드러났다.

| 쪼갠 것 | 내용 | 누가 보장하나 |
|---|---|---|
| **원자성** | 판정과 변경 사이에 남이 끼어들지 못하게 | **DB 락** — `ORDER BY id FOR UPDATE` (ADR-0002, 이미 확정) |
| **판정** | 이 6석이 지금 잡을 수 있는가 · 1~6석인가 · 중복은 없나 | **이 ADR 이 정하는 것** |

그 시점의 제약은 이랬다.

| 제약 | 출처 |
|---|---|
| 락 범위는 **좌석 행**이다. 운행 전체를 잠그면 800석짜리 열차의 처리량이 1로 떨어진다 | `data.md` §4.1 |
| `trip_seat` + `seat_hold` 는 **한 트랜잭션 묶음**으로 이미 정의돼 있다 | `data.md` §5.6 |
| `409` 응답이 실패 사유를 둘로 나눈다 — `HELD_BY_OTHER` 와 **`ALL_OR_NOTHING`** | `api/components/holds.yaml` |
| `:domain` 은 의존성 0 · DB 없이 테스트 가능해야 한다 | ADR-0001 |

가장 먼저 떠오른 모양은 유스케이스의 반복문이었고, 세 군데가 깨졌다.

| # | 문제 |
|---|---|
| ① | **검사와 변경이 한 루프에** 있으면 4번째 좌석에서 실패할 때 앞의 3석이 이미 `HELD` 로 바뀐 뒤다. DB 는 롤백되지만 **메모리 객체는 반쯤 바뀐 채** 남고, 커밋 후 SSE 발행이 그 객체를 보면 잡히지도 않은 좌석을 방송한다 |
| ② | **`new Hold(...)` 가 열려 있다.** 규칙을 안 거친 `Hold` 를 누구나 만들 수 있고, 제일 먼저 그렇게 하는 것은 테스트 픽스처다 |
| ③ | `:domain` 을 떼어낸 이유가 **DB 없이 규칙을 테스트하려는 것**이었는데, 정작 핵심 규칙이 `:application` 에 남는다 |

## 검토한 대안

| 대안 | 장점 | 단점 | 판정 |
|---|---|---|---|
| **`Hold` 의 정적 팩토리** — 생성자를 `private` 으로 막고 `Hold.open(…)` 하나만 문을 연다 | **`Hold` 객체의 존재 자체가 규칙을 통과했다는 증명**이 된다. 다른 경로가 없다 | 팩토리가 `Seat` 까지 바꾼다 — "한 트랜잭션 = 한 애그리거트" 를 포기한다 | ✅ **채택** |
| `Trip` 애그리거트 — `trip.hold(seats)` | 교과서적 DDD. 애그리거트가 곧 정합성 단위 | **애그리거트를 트랜잭션 경계로 삼으면 운행 하나가 직렬화된다.** `data.md` §4.1 이 "운행 전체 락"을 버린 것과 같은 이유로 버린다 | ❌ |
| 도메인 서비스 — `SeatHoldPolicy.judge(seats)` | 규칙이 `:domain` 으로 들어온다 | **②가 그대로 남는다.** 규칙을 통과한 `Hold` 와 안 통과한 `Hold` 가 **타입으로 구분되지 않는다** | ❌ |
| 유스케이스의 반복문 | 가장 짧다 | ①②③ 전부 | ❌ |

## 결정

> **규칙은 `Hold.open` 안에 있고, 그 밖으로 나가는 문은 없다.**

```java
public static Hold open(HoldId id, TripId tripId, MemberId memberId,
                        List<Seat> seats, Instant now) {
    requireShape(seats);                         // ① 1~6석 · 중복 없음 · 같은 운행
    List<SeatFailure> failures = judge(seats);   // ② 전수 판정
    if (!failures.isEmpty())
        throw new SeatUnavailable(failures);     //    아직 아무것도 안 바꿨다
    Hold hold = new Hold(id, tripId, memberId,
                         addressesOf(seats), now.plus(TTL));
    seats.forEach(s -> s.markHeld(id));          // ③ 변경은 판정이 끝난 뒤에만
    return hold;
}
```

**②와 ③ 사이의 줄바꿈이 이 결정의 급소다.** 도메인은 **부분 변경이 메모리에서조차 없음**을, 락은 **그 사이 아무도 끼어들지 못함**을 보장한다. 둘이 합쳐져야 초과 판매 0건이다.

**`SeatUnavailable` 이 `List<SeatFailure>` 를 동봉하는 것도 이 결정의 일부다.** 계약의 `ALL_OR_NOTHING`("이 좌석은 멀쩡한데 같이 고른 좌석 때문에 함께 실패했다")은 **전수 판정을 한 쪽만 알 수 있다.** 판정을 흩뜨리면 이 응답을 만들 수 없다.

**시그니처가 결정적인 것도 의도다.** 랜덤(`HoldId`)과 시계(`now`)를 밖에서 받으므로 `open` 은 같은 입력에 같은 결과를 낸다 — 테스트가 ID 를 고정하고 만료 창을 자유롭게 민다.

## 결과

| 얻은 것 | 잃은 것 |
|---|---|
| **규칙을 우회하는 경로가 타입 수준에서 없다** | **"한 트랜잭션 = 한 애그리거트" 를 포기했다** — 애그리거트는 규칙 경계지 트랜잭션 경계가 아니다 |
| 핵심 규칙이 DB 없이 테스트된다 | 팩토리 인자가 5개다 |
| `409` 의 두 사유를 만들 수 있다 | `Hold.open` 이 `Seat` 를 바꾼다는 사실을 읽는 사람이 알아야 한다 |
| 부분 변경이 메모리에서도 불가능하다 | |

> **"한 트랜잭션 = 한 애그리거트" 를 포기한 것이 이 ADR 에서 가장 논쟁적인 부분이다.** 그 규칙은 애그리거트를 정합성 단위로 삼을 때 성립하는데, 우리는 정합성을 **DB 락**이 만들고 애그리거트는 **규칙을 담는 그릇**으로만 쓴다. 규칙을 따르려고 `Hold` 와 `Seat` 를 떼어놓으면 ①의 부분 변경 경로가 다시 열린다.

## 되돌린다면

| 항목 | 비용 |
|---|---|
| 바꿔야 할 것 | `Hold` · `Seat` · `HoldSeatsService` · 그 테스트 |
| 파급 | `:application` 의 선점·확정·회수 **세 경로**가 같이 흔들린다. `409` 응답 조립도 |
| **비싼 이유** | **애그리거트 경계는 그 위에 쌓인 모든 코드의 전제**다. 경계를 옮기면 "어디서 판정하나" 가 전부 다시 정해지고, **이미 통과하던 동시성 테스트가 무엇을 증명하는지도 바뀐다** |
