# ADR-0004 — SSE 팬아웃을 Redis Stream 단독으로 한다

| | |
|---|---|
| 상태 | 채택 |
| 날짜 | 2026-09-09 |
| 대체 | 초기안 — Redis Pub/Sub 팬아웃 (ADR 없음) |
| 관련 문서 | [api.md §6](../api.md) · [data.md §6.4](../data.md) · [redis-workloads](../diagrams/redis-workloads.html) |

## 맥락

앱 서버가 여러 대면 **선점을 처리한 서버와 SSE 연결을 들고 있는 서버가 다르다.** 초기안은 **Redis Pub/Sub**으로 서버 간 팬아웃을 하는 것이었고, `CLAUDE.md`와 다이어그램 3개에 그렇게 적혀 있었다.

`api.md` §6에서 **SSE 재개 계약**을 정하면서 조건이 하나 늘었다.

| 결정 | 내용 |
|---|---|
| 재개 | `Last-Event-ID` → 그 다음 건부터 재생 |
| **보관** | **운행당 최근 1000건** |

이 순간 Pub/Sub은 요구를 만족할 수 없게 됐다.

## 검토한 대안

| 대안 | 팬아웃 | **재개(보관)** | 판정 |
|---|---|---|---|
| Pub/Sub 단독 | ✅ | ❌ **불가** — 보관을 안 한다 | ❌ |
| Pub/Sub + Stream 병행 | ✅ | ✅ | ❌ **이중 기록** |
| **Stream 단독** | ✅ | ✅ | ✅ **채택** |

## 결정

> **`XADD` 한 번으로 서버 간 팬아웃과 재개용 보관을 동시에 해결한다.**

```
서버 A: 트랜잭션 커밋
   └─ afterCommit ─┬─ 캐시 무효화
                   └─ XADD trip:101:events MAXLEN ~ 1000
                            │
        ┌───────────────────┼───────────────────┐
     서버 A              서버 B              서버 C     (XREAD BLOCK)
```

| 항목 | 값 |
|---|---|
| 키 | `trip:{tripId}:events` |
| 보관 | `MAXLEN ~ 1000` — **근사 트리밍** (정확한 트리밍은 매 `XADD`에 지연을 붙인다) |
| 소비 | 서버마다 `XREAD BLOCK` — **Consumer Group 아님** |
| 이벤트 ID | Redis 생성 `<ms>-<seq>` — **그대로 클라이언트에 노출** |

**Consumer Group을 안 쓴다.** 그건 여러 워커가 일을 **나눠 갖는** 구조인데, 여기서는 **모든 서버가 모든 이벤트를 받아야** 자기 SSE 연결에 쓸 수 있다. 나눠 가지면 팬아웃이 깨진다.

**병행을 버린 이유** — 같은 이벤트를 두 번 기록하면 **순서가 어긋날 여지**가 생기고, 어느 쪽이 진실인지 정해야 하는 문제가 새로 생긴다.

## 결과

| 얻은 것 | 잃은 것 |
|---|---|
| 팬아웃과 재개가 **한 자료구조** | Pub/Sub보다 메모리를 쓴다 (최악 ~120MB) |
| 이벤트 ID가 **재개 커서 그 자체** | Stream 소비 루프를 직접 짜야 함 |
| `resume-failed` 신호의 근거가 명확 | |

**파급** — `CLAUDE.md` · `features.md` `F-18` · `tech.md` · `data.md` · 다이어그램 3개를 함께 고쳤다.

## 되돌린다면

| 항목 | 비용 |
|---|---|
| 바꿔야 할 것 | `:adapter-cache` 구현 · Redis 키 구조 |
| **비싼 이유** | **없다 — 싸다.** `:application`은 포트만 보므로 어댑터 교체로 끝난다 |

> **되돌리기 싸다는 것도 정보다.** ADR로 남기는 이유는 되돌리기 어려워서가 아니라, **"왜 Pub/Sub이 아닌가"를 6개월 뒤에 반드시 다시 묻게 되기 때문**이다.
