## 코레일 전산망

### 계보

| 시스템 | 역할 | 시기 |
|---|---|---|
| **KROKET** | 승차권 발권 전산 (예매 백본) | 2기 전산망 **2004.4.1 ~ 현재** |
| KROIS → XROIS → NXROIS | 철도운영정보 | 1996 → 2011 → 2025 시범 |
| TIDS | 여객행선안내. XROIS에서 **잔여석** 수신 → 역별 서버 → 전광판 | 2003~ |
| 레츠코레일 | 예매 웹사이트 | ~ 2025.2.24 (홈페이지 통합) |
| 코레일톡 / 코레일+ | 모바일 앱 | 2026.8.3 통합 |

> 예매 백본은 KTX 개통(2004)에 맞춘 "차세대 통합정보시스템" 계보. **프론트만 교체를 반복했고 발권 전산은 20년 넘게 유지.** XROIS는 2026년에도 IE 의존.

### 구조 (관측·추론)

```
역 창구(KROKET) · 자동발매기 · 전화예매(ARS)  →  철도 전용망(인트라넷)  ┐
인터넷 예매(레츠코레일)                        →  인터넷 웹 서버        ┴→ 예약·발권 업무 서버
                                                                          ├→ 카드 승인 VAN (동기)
                                                                          └→ 중앙 DB → KROIS → TIDS → 역 전광판
```

| 구분 | 항목 |
|---|---|
| **확인됨** | 4개 채널, 역무 계열과 고객 계열의 물리적 분리, 카드 승인 동기 호출, KROIS→TIDS 잔여석 전달 |
| **추론** | 중앙 DB 단일 구성, 전 구간 동기, DB 락 기반 선점, 웹 서버 계층 |

> **역무 계열과 고객 계열 분리의 근거** — 과거 현장 예매는 홈페이지보다 2시간 늦게 시작했다. *"고객 서버는 터져도 상관없는 편이나, 역무 서버가 터지면 열차 운행에 차질이 생기고 최악의 경우 대한민국 철도가 통째로 마비"*

### 유량 제어 8가지 — 기술이 아니라 운영

| # | 기법 | 내용 |
|---|---|---|
| 1 | **노선별 날짜 샤딩** | 2026 추석: 9/7 일반열차 → 9/8 경전·강릉·동해·중앙·중부내륙 KTX → 9/9 호남·전라 KTX → 9/10 수서 출도착 → 9/11 경부선 KTX |
| 2 | **그룹별 시간대 분리** | 교통지원대상 09~15시 / 일반 07~13시 |
| 3 | **예매·결제 시간 분리** | 예매만 먼저, 결제는 별도 3일. 미결제 자동취소. *사유: "예약 트래픽과 결제 트래픽이 뒤엉키면 서버가 뻗는다"* |
| 4 | 채널 단일화 | 2020 추석부터 현장 예매 전면 폐지 |
| 5 | 수량 제한 | 1인 편도 6매 / 왕복 12매 |
| 6 | 단거리 구간 차단 | 근거리 구간 예매 불가 |
| 7 | 전용 랜딩 UI | 명절엔 UI 교체 + 서버 확장 |
| 8 | 비회원 차단 | 회원번호 로그인 필수 |

> **가장 싸고 확실한 해법은 기술 밖에 있었다.** 트래픽을 5일로 쪼개면 서버를 안 늘려도 1/5이 된다. 다만 이건 공공서비스라 가능한 카드이고, 콘서트 티켓팅에는 쓸 수 없다.

### 평시 예매 흐름

| 코레일 동작 | 대응 개념 |
|---|---|
| 좌석 선택 → 예약 (결제 전) | `HOLD` |
| **10분 내 미결제 시 자동취소** | HOLD TTL = 10분 |
| 장바구니 담아도 선점권 없음 | 담기 ≠ 잡기 |
| 결제 완료 | `CONFIRM` |
| 명절 결제기간 3일 | 이벤트별 TTL 차등 |

### 2025.9.17 장애

| 항목 | 내용 |
|---|---|
| 시각 | 오전 7시 예매 시작 직후, **2시간 이상** |
| 증상 | PC 웹 빈 화면 / 앱 "사용자가 많아 대기 중" 반복 / "통신 중 오류 발생" |
| 대기번호 | 10~20만, 일부 **100만번대**. 대기 인원 표시는 **99,999에서 포화** |
| 공식 입장 | "예매객이 동시에 몰려 부하 발생 **추정**", 원인 조사 중 |
| 대응 | 예매 시간 오후 4시까지 연장 |
| 악화 요인 | 무궁화호 사고로 일정 **2주 연기** → 수요 집중 / 증편 축소 |
| 이력 | 2023.12에도 동일 유형 |

**분석**

| 증상 | 터진 위치 |
|---|---|
| PC 웹 빈 화면 | 대기열 **앞단** (웹서버·정적 자원) |
| 순번이 줄지 않음 | **승급 정지** = 예매 서버 소화 불가 |
| 통신 중 오류 | 백엔드 타임아웃 |

> **대기번호 100만 ≠ 잘 버팀.** 번호 발급은 `INCR` O(1)이라 원래 쉽다.
> **대기열 부하의 실체는 폴링이다.** 진입은 1인 1회지만 폴링은 지속 — 100만 명이 3초 주기면 **초당 33만 요청**.
> **대기 인원이 99,999에서 포화**되는 건 카운터 기반 구현을 시사(추정).

## 타사 사례

### 국내

| 기업 | 대상 | 대기열 | 재고 처리 | 비동기 | 특이점 |
|---|---|---|---|---|---|
| 인터파크 티켓 | 공연 | 있음 | `AVAILABLE / ON HOLD / BOOKED` + `expired_at` | 불명 | 대형 이벤트 시 **별도 랜딩 페이지**. 만료표를 **cron 배치로 회수**하는 것으로 추정 ('오류표' 현상) |
| 배달의민족 | 선착순 쿠폰 | **Redis Sorted Set** | — | — | 앞단 **주문 라우터**로 대상 업소만 라우팅 격리 |
| 여기어때 (네고왕) | 쿠폰 | — | **Redis Lua** (재고+중복 원자화) | **Kafka** | API가 **DB 미접근**, 지급 가부만 응답. **동접 28,800 / TPS 3,600 무장애** |
| 원더월(노머스) | 굿즈·티켓 | **Redis 카운터 3개** | — | SQS 버퍼 | AWS VWR 변형. **10만 동접 부하테스트** |

**원더월 카운터 방식**

| 키 | 역할 |
|---|---|
| `QUEUE_COUNTER` | 요청마다 +1 → 대기번호 |
| `SERVING_COUNTER` | 초기값 = 동시 허용 인원. 완료자 발생 시 +1 |
| `TOKEN_COUNTER` | 발급 토큰 수 추적 |

**원더월 부하테스트 교훈**

| 문제 | 조치 |
|---|---|
| API Gateway RPS 1만 한계 | ALB로 교체 |
| Lambda cold start · 재사용 편차로 latency 불균일 | ECS Fargate로 교체 |
| Locust 부하분산기 자체 지연으로 p99 왜곡 | 점진 증가 테스트 병행 |
| **Redis는 싱글 스레드 — 스케일업 무효** | **replica 추가(스케일 아웃)** |
| 토큰 받고 이탈 | Redis keyspace notification |

### 해외

| 서비스 | 방식 | 특이점 |
|---|---|---|
| **Ticketmaster** | Smart Queue | 판매 **15~30분 전** 대기실 오픈 → 시작 시 **무작위 배정**(봇 속도 우위 제거) → 이후 FIFO. 동시 쇼핑 **수백 명**. 차례 시 **10분 홀드** |
| **Queue-it** | 3가지 모드 | ① 예정 판매(사전 대기실+랜덤) ② **Safety net**(임계치 도달 시에만 활성) ③ 선입장. **대기자를 제공자 서버에 호스팅 → 원 서비스에 부하 0** |
| **AWS Virtual Waiting Room** | 레퍼런스 | API GW ×2 + Lambda + SQS + DynamoDB + ElastiCache. 목적 = **JWT 발급 통제** |

### 공통 패턴

| 패턴 | 근거 |
|---|---|
| 대기열은 원 서비스와 **물리적으로 분리된 인프라** | Queue-it · 인터파크 · 원더월 |
| outflow rate는 **운영자가 조절하는 값** | Rock in Rio(수동) · Ticketmaster(수백 명) · 원더월(SERVING_COUNTER) |
| 입장은 **토큰**으로 통제 | AWS(JWT) · 원더월(서비스 토큰) · Queue-it(Queue token) |
| 재고 판정은 **원자 연산** | 여기어때(Lua) · 인터파크(Redis Lock 추정) |
| **이탈자·만료 회수** 장치 필수 | 원더월(keyspace notification) · 인터파크(cron) · Ticketmaster(10분 홀드) |

### 대기열 자료구조 두 유파

| | **Sorted Set** (배민) | **Counter** (원더월 · AWS) |
|---|---|---|
| 방식 | ZSET, member=userId, score=순번 | INCR로 번호만 발급 |
| 순번 조회 | `ZRANK` — O(log N), **정확** | `내번호 − SERVING` — O(1), 근사 |
| 메모리 | 대기자 수에 비례 | 거의 0 |
| 이탈자 처리 | `ZREM` 즉시 가능 | 어려움 |
| 중복 진입 차단 | `ZADD NX` | 별도 저장소 필요 |
