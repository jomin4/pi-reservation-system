# 핵심 기능 상세

## F-04 좌석 선점

| 항목 | 규칙 |
|---|---|
| 최대 좌석 수 | 6석 |
| 원자성 | **전부 성공 또는 전부 실패.** 부분 성공 없음 |
| TTL | 10분 |
| 판정 근거 | PostgreSQL만 |
| 동시 요청 | 같은 좌석에 N건 → 정확히 1건 성공, 나머지 `409` |
| 만료 판정 | 30초 스케줄러 + 조회 시점 lazy 판정 이중 |

> **의도** — Redis 좌석맵은 **조회 가속용이지 판정 근거가 아니다.** 캐시를 보고 선점을 허용하면 캐시 지연만큼 초과 판매가 난다. 캐시는 틀릴 수 있고 DB는 틀리면 안 된다.

**API 계약 요구** — `409` 응답 본문에 **어느 좌석이 왜 실패했는지** 목록이 들어와야 한다. 클라이언트가 "7B는 남이 가져갔고 7A도 함께 실패했다"를 정확히 안내하려면 필요하다.

## F-08 · F-09 결제 · 확정

| 단계 | 처리 | 실패 시 |
|---|---|---|
| 1 | 선점 유효성 확인 | TTL 만료면 `410` |
| 2 | 토스페이먼츠 승인 요청 | — |
| 3 | 승인 성공 → 예약 생성 · 좌석 `SOLD` | — |
| 4 | 승인 거절 | **선점 유지.** 다른 수단으로 재시도 가능 |
| 5 | **응답 타임아웃** | 멱등키로 승인 상태 재조회 후 판정 |
| 6 | **승인됐는데 확정 실패** | 보상 취소 후 선점 반환 |

> **의도** — 외부 결제와 내부 DB 사이에 분산 트랜잭션이 없다. 5·6번을 **멱등키 + 상태 재조회 + 보상**으로만 맞춘다. 이 셋이 이 시스템에서 가장 어려운 부분이고, 코레일이 예매와 결제를 3일 간격으로 분리한 이유이기도 하다.

| 결정 | 값 |
|---|---|
| PG | **토스페이먼츠** 단일 |
| 결제창 | 웹·모바일 모두 **인앱 · 인브라우저 결제창** |
| 멱등키 | 결제 화면 진입 시 **1회 생성** · 재시도에도 같은 값 |
| 모바일 멱등키 저장 | **영속 저장**(SecureStore 등). 앱이 죽으면 메모리 키는 사라진다 |
| 외부 경로 | 앱 서버 → **DMZ 아웃바운드 프록시** → 토스 |

> **QR 위임 결제는 폐기됐다**(2026-09-04). 키오스크 전용 방식이었다.

## F-09 예약번호

| 항목 | 값 |
|---|---|
| 형식 | **8자리 숫자 · 무작위** (순번 아님). 표시는 `1234 5678` |
| 용도 | 사용자가 자기 예약을 식별·문의할 때 쓰는 번호 |
| 조회 열쇠 | **아니다.** 조회는 로그인(`F-12`)으로만 한다 |

> **의도 — 왜 순번이 아닌가.** 조회 열쇠가 아니라 대입 위험은 낮지만, 순번이면 **누적 예약 건수가 그대로 노출**된다. 무작위 8자리면 그 정보가 새지 않고 읽기도 쉽다.

## F-14 · F-15 취소 · 환불

| 항목 | 규칙 |
|---|---|
| 취소 가능 시점 | 출발 시각 이전 |
| 좌석 | 즉시 `AVAILABLE` 반환 + SSE 전파 |
| 예약 | 삭제하지 않고 `CANCELLED` |
| 환불 | 토스페이먼츠 결제취소 API (`F-15`) |
| 위약금 · 부분 환불 | 범위 밖. 전액 환불만 |

> 취소 즉시 해당 운행을 보고 있는 **모든 화면에 SSE로 좌석 복귀가 전파**된다. 시연에서 가장 보여주기 좋은 장면이다.

## F-16 ~ F-19 실시간 전파

| 항목 | 규칙 |
|---|---|
| 구독 단위 | 운행(trip) 1건 |
| 이벤트 | 좌석 상태 변경 (`HELD` / `SOLD` / `AVAILABLE`) |
| 전파 경로 | 앱 → Redis Stream → 전 앱 서버 → 각 SSE 연결 |
| 하트비트 | 15초 주기 comment 프레임 |
| 캐시 무효화 | **같은 이벤트로 처리** |

> **의도** — 캐시 무효화와 실시간 전파를 **분리하지 않는다.** 두 경로로 나누면 "화면은 바뀌었는데 캐시는 옛날 값"이 생긴다. 좌석 변경 이벤트 하나가 두 일을 다 한다.

**API 계약 요구** — `Last-Event-ID` 재개가 **서버 보관 범위를 벗어났을 때** 클라이언트가 그걸 구분할 수 있어야 한다. 재개 실패를 성공인 척하면 좌석맵에 구멍이 남는다. 모바일은 백그라운드가 길어 이 경로가 예외가 아니라 일상이다.

## F-36 인증 시도 제한

| 항목 | 값 |
|---|---|
| 대상 | `F-24` 로그인 |
| 임계 | 5회 |
| 조치 | **영구 잠금이 아니라 5분 일시 차단 후 자동 해제** |
| 저장 | Redis (TTL 네이티브) |

> **의도** — 코레일은 5회 실패 시 영구 잠금하고 비밀번호 재설정으로 푼다. **우리는 재설정이 범위 밖이라 잠기는 순간 계정이 영구 사망한다.** 그래서 시간 기반이어야 한다. 부수적으로 **자동화된 반복 로그인이 자기 계정을 잠그고 죽는 사고**도 막는다.

## 인증 기술 결정

| 항목 | 선택 | 근거 |
|---|---|---|
| 비밀번호 해싱 | BCrypt (cost 10~12) | Spring Security Crypto 표준 |
| Access 토큰 | JWT · 15분 · 무상태 검증 | 매 요청 DB 조회 회피 |
| Refresh 토큰 | 14일 · **Redis 저장** · 회전 | TTL 네이티브. 로그아웃 시 삭제로 무효화 |
| 인가 판정 위치 | `:application` 유스케이스 진입부 | 컨트롤러에 두면 클라이언트마다 중복 |
| 시도 제한 | 5회 → **5분 일시 차단** (Redis) | 재설정 수단이 없어 영구 잠금은 불가 |

> Redis가 죽으면 Refresh가 사라져 재로그인이 필요하다. **좌석 판정에는 영향 없다**는 점이 이 선택의 전제다.

## 초기 범위 밖

| 제외 | 이유 |
|---|---|
| **현장 발권 (키오스크)** | 하드웨어 확보와 오프라인 결제 계약이 현실적으로 불가능 |

| 예매 오픈 시각 게이트 | 폭주 재현 수단이 초기 범위 밖 |
