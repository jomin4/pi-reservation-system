# 프로젝트 개요

## 정의

> **코레일 전산망 구조를 벤치마킹해 현대 기술로 재구성한, 폐쇄망 기반 좌석 예매 시스템**

기능을 베끼는 것이 아니라 **그 시스템이 풀어야 했던 문제를 다시 푸는 것**이 목표다. 그 문제는 하나로 요약된다.

> **여러 요청이 같은 좌석을 동시에 노릴 때, 정확히 하나만 성공시키는 것.**

## 배경

코레일 여객 발권 전산은 2004년 KTX 개통에 맞춰 도입된 체계를 지금까지 쓰고 있다. 프론트(웹사이트·앱)는 여러 번 교체됐지만 발권 백본의 계보는 20년 넘게 유지된다.

| 관측된 사실 | 출처 |
|---|---|
| 예매 백본은 2004년 도입 체계 | 전산망 계보 |
| 명절 예매 시 반복적 접속 장애 (2023, 2025) | 언론 보도 |
| 트래픽을 **노선별 날짜 5일 분산**이라는 운영 정책으로 흡수 | 예매 일정 공고 |
| 예매와 결제를 **3일 간격으로 분리** | 예매 안내 |
| 역무 계열과 고객 계열을 **물리적으로 분리** | 현장 예매 운영 방식 |

이 시스템이 실제로 풀고 있는 문제를, 지금 쓸 수 있는 기술로 다시 설계한다.

## 벤치마킹 대상 구조

| 코레일 | 역할 |
|---|---|
| 인터넷 예매 · 모바일 앱 | 다중 클라이언트 진입 |
| 철도 전용망 / 인터넷 구간 분리 | **장애 격리** |
| 예약·발권 업무 서버 | **단일 판정 지점** |
| 중앙 데이터베이스 | 좌석·예약 원장 |
| 카드 승인 VAN (동기 호출) | 외부 연동 |
| KROIS → TIDS → 역 전광판 | **잔여석 전파** |

> 역 창구·자동발매기 같은 **현장 발권 계열은 이 프로젝트의 범위 밖**이다. 하드웨어 확보와 오프라인 결제 계약이 현실적으로 불가능해서다 — [범위 밖](#범위-밖) 참조.

## 무엇을 현대화하는가

| 축 | 코레일의 해법 | 이 프로젝트 |
|---|---|---|
| **좌석 동시성** | DB 락 (추정) | **PostgreSQL 비관적 락 + CAS 가드** |
| 조회 부하 | 매 요청 DB 직격 | **Redis 캐시** |
| 잔여석 전파 | 배치 (KROIS → TIDS → 전광판) | **SSE 실시간 푸시** |
| 장애 격리 | 역무망 / 고객망 물리 분리 | **Docker 네트워크 분리 + 폐쇄망** |
| 오픈 시각 폭주 | 노선별 날짜 분산 (운영 정책) | **범위 밖** — 초기 릴리스에서 다루지 않는다 |
| 외부 결제 | 전용선 VAN | **아웃바운드 프록시 화이트리스트** |
| 배포·운영 | 비공개 | **IaC + CI/CD 자동화** |

## 클라이언트

| 클라이언트 | 네트워크 | 인증 |
|---|---|---|
| 웹 (React 19 + Vite) | 인터넷 → Cloudflare | JWT |
| 모바일 (React Native → APK) | 인터넷 → Cloudflare | JWT |

두 클라이언트는 **같은 API를 쓴다.** 화면과 동선은 다르지만 서버가 보는 요청은 동일하다.

> **동시성은 클라이언트가 만드는 게 아니라 서버가 감당하는 것이다.** 웹·모바일은 같은 좌석을 노리는 두 사용자를 **눈으로 보여주는** 역할이고, 정확히 하나만 성공한다는 보장은 화면이 아니라 **DB 락과 상태 전이**가 한다. 대규모 경합을 인위적으로 만드는 수단은 초기 범위 밖이다.

# 이 프로젝트가 푸는 어려운 문제

## 1. 좌석 동시성 — 핵심

> **N개 요청이 같은 좌석을 동시에 노릴 때 정확히 1건만 성공해야 한다.**

여기에 두 겹의 어려움이 더 붙는다.

| 겹 | 내용 |
|---|---|
| **원자성** | 6석을 한 덩어리로 잡는다. **전부 성공 또는 전부 실패** — 부분 성공이 없다 |
| **잠금 순서** | 두 요청이 같은 좌석 집합을 반대 순서로 잠그면 데드락. 결정론적 순서가 필요하다 |
| 만료 회수 | TTL 10분이 지난 선점을 되돌려야 하는데, 회수와 확정이 부딪힐 수 있다 |

검증 기준은 하나다 — **초과 판매 0건.** `data.md` §4.9의 대사 쿼리가 0행을 반환해야 한다. **부하를 어떻게 만들지는 초기 범위 밖**이고, 기준 자체는 바뀌지 않는다.

## 2. 외부 결제와 내부 DB 사이의 정합성

분산 트랜잭션이 없다. 결제 승인은 외부에서 나고 좌석 확정은 내부에서 난다.

| 상황 | 처리 |
|---|---|
| 승인 거절 | 선점 유지 · 재시도 가능 |
| **응답 타임아웃** | 승인됐는지 모른다 → **멱등키로 상태 재조회** |
| **승인됐는데 확정 실패** | **보상 취소** 후 선점 반환 |

뒤의 둘이 이 시스템에서 가장 어려운 구간이다. 코레일이 예매와 결제를 3일 간격으로 분리한 이유이기도 하다.

## 3. 실시간 전파

좌석 하나가 팔리면 **그 좌석을 보고 있는 모든 화면**이 즉시 바뀌어야 한다.

| 과제 |
|---|
| 앱 서버가 2대인데 SSE 연결은 한 대에만 붙어 있다 → **서버 간 전파** |
| 캐시 무효화와 실시간 전파를 **같은 이벤트**로 처리 |
| 연결 유지 비용 — SSE N개를 붙잡은 채 예매 처리량이 얼마나 떨어지는가 |
| Cloudflare Tunnel 유휴 타임아웃 → **하트비트 필요** |
| 모바일 앱이 백그라운드로 가면 연결이 끊긴다 → 복귀 시 전체 재조회 |

## 4. 폐쇄망 운영

인터넷이 끊긴 환경에서 시스템을 운영·배포·갱신하는 문제.

| # | 과제 |
|---|---|
| 1 | 의존성 공급 — Maven·npm·apt를 어디서 받는가 |
| 2 | 컨테이너 이미지 반입 |
| 3 | 사설 CA — 공인 CA를 못 쓰는 환경의 인증서 |
| 4 | 내부 NTP — 분산 시스템에서 시계 |
| 5 | **인바운드 없이 배포** — CD를 pull 방식으로 |
| 6 | **외부 결제 연동** — 폐쇄망에 구멍을 어떻게 안전하게 뚫는가 |

## 범위 밖

의도적으로 제외한다. 핵심 문제의 밀도를 지키기 위해서다.

| 제외 | 이유 |
|---|---|
| **현장 발권 (키오스크 · 무인 단말)** | **하드웨어 확보와 오프라인 카드 결제 계약이 현실적으로 불가능.** 2026-09-04 철회 |
| **비회원 예매** | 위와 함께 철회. 예매는 로그인 회원만 |
| AI 기능 | 동시성·정합성이라는 핵심이 희석됨 |
| 게임 요소 | 도메인과 무관 |
| 좌석 구간 판매 (서울→대전 / 대전→부산) | 복잡도 대비 학습 가치. **확장 후보로 보류** |
| 마일리지 · 할인 · 좌석 등급 | 부하·정합성과 무관 |
| 이메일 인증 · 비밀번호 재설정 · 변경 | 폐쇄망 SMTP 회피 |
| iOS 배포 | Android APK만 |
| Kubernetes | VM 자원 한계. Docker Compose로 충분 |
| MSA | 폐쇄망 소규모에 과함. 모듈러 모놀리스 |

> **키오스크 철회로 잃은 것을 정직하게 적어둔다** — mTLS 디바이스 인증, 임베디드 C 에이전트, ESC/POS 실물 출력, 그리고 "인증 방식이 다른 채널을 하나의 Principal로 환원한다"는 인가 설계. 남은 인증 경로는 JWT 하나다.
