주석

  • 좌석 주소 체계는 미확정이다. 여기서는 실물 KTX 방식(호차 + 행 + A/B/C/D, 창측 A·D)으로 그렸다. 일련번호 방식으로 정해지면 호차 탭이 사라지고 격자 하나가 된다.
  • 격자는 4×9로 축약해 그렸다. 실제 KTX-1은 20량 935석이라 호차당 좌석 수와 배열은 시드 데이터를 따른다.
  • SSE 연결 상태를 항상 노출한다(F-16). 끊긴 채로 옛 좌석맵을 보고 있으면 선점이 계속 실패하는데 사용자는 이유를 모른다. 끊기면 배지가 빨강 + "재연결 중"으로 바뀐다.
  • 하트비트 15초(F-17)는 UI에 안 보이지만, 끊김 감지 근거다.
  • 다른 사람이 선점한 좌석은 빗금으로 표시한다 — 판매 완료(회색)와 구분해야 한다. 선점은 10분 뒤 풀릴 수 있는 임시 상태다.
  • 6석 도달 시 나머지 좌석은 클릭해도 무시. 카운터를 2 / 6으로 상시 노출한다.
  • 비로그인 상태에서 "좌석 선점하기"를 누르면 W-07 로그인으로 보낸 뒤 이 화면으로 복귀한다. 예매는 로그인 회원만 가능하다 — 비회원 예매는 2026-09-04 철회됐다.

주의 — 범위 밖 링크를 넣지 말 것

  • "비밀번호를 잊으셨나요?" 링크가 없다. 비밀번호 재설정은 초기 범위 밖이다(폐쇄망 SMTP 회피). 관습적으로 넣기 쉬운 자리라 명시해둔다.
  • redirect 파라미터로 원래 화면(대개 W-03)에 복귀한다. 선점 직전에 로그인으로 튕겼다가 좌석 선택을 잃으면 안 된다 — 선택 좌석은 세션 스토리지에 보존.
  • Access 15분 / Refresh 14일. 토큰 저장 위치(메모리 vs 쿠키)는 프론트 설계 단계에서 정한다.
  • F-36 시도 제한은 잠금이 아니라 5분 일시 차단이다. 비밀번호 재설정이 없으므로 영구 잠금이면 계정이 그대로 죽는다. 그래서 안내 문구도 "계정이 잠겼습니다"가 아니라 "5분 뒤 다시 시도하세요"여야 한다.
  • 남은 횟수(3 / 5회)를 노출할지는 판단이 갈린다. 노출하면 사용자가 예측 가능하고, 숨기면 공격자에게 정보를 덜 준다. 여기서는 노출로 그렸다 — 재설정 수단이 없는 상태에서 경고 없이 차단되면 사용자가 손쓸 방법이 없다.

  • 비밀번호 변경도 범위 밖으로 뺐다. 재설정(메일 발송 필요)에 이어 변경까지 빠지면서, 가입 시 정한 비밀번호를 사용자가 바꿀 수단이 전혀 없는 상태가 된다. 의도된 축소이지 누락이 아니다 — 인증은 최소형으로 시작해 점차 추가한다.
  • 이 화면에 남는 건 이름·연락처 수정뿐이다. 그래서 W-12는 P1 중에서도 가장 뒤로 밀어도 된다.
  • 회원 탈퇴도 범위 밖.

예외 상태

이 시스템에서 실제로 자주 발생하는 3가지. 정상 흐름보다 이쪽이 설계 난이도가 높다.

E-01 선점 충돌 F-04 → 409

W-03에서 선점을 눌렀는데 그 사이 다른 채널이 좌석을 가져간 경우.

/trips/KTX-101/seats

좌석을 잡지 못했습니다

4호차 7B 좌석을 다른 고객이 먼저 선택했습니다.
함께 선택한 7A도 선점되지 않았습니다.

선택한 좌석은 전부 함께 잡히거나 전부 실패합니다.
일부만 잡힌 상태로 남지 않습니다.

주석 — 전부 성공 또는 전부 실패

  • 이 화면이 F-04의 원자성을 사용자에게 설명하는 자리다. "7B는 실패, 7A는 성공"이 없다는 걸 명시적으로 말해야 한다. 안 그러면 사용자는 7A가 잡혔다고 착각하고 다시 시도해 중복 선점을 만든다.
  • 서버 응답에 어느 좌석이 왜 실패했는지가 들어와야 이 문구를 만들 수 있다. 409 본문에 실패 좌석 목록을 담는 계약이 필요하다 — api.md 작성 시 반영.
  • 모달을 닫으면 좌석맵이 최신 상태로 갱신되어 있다(SSE가 이미 반영). 실패 직후 화면이 옛 상태면 사용자는 같은 좌석을 또 누른다.
  • "같은 좌석 다시 시도"는 상대 선점이 10분 뒤 풀릴 수 있으므로 의미가 있다. 다만 즉시 재시도는 거의 실패하므로 연타 방지 필요.

E-02 선점 만료 F-07 → 410

10분이 지나 좌석이 회수된 경우.

/holds/h_8f3a21

선점 시간이 만료되었습니다

10분 안에 결제가 완료되지 않아 4호차 7A, 7B 좌석이 반환되었습니다.
결제는 진행되지 않았습니다.

주석

  • 만료 판정은 스케줄러(30초 주기)와 요청 시점 lazy 판정 둘 다가 한다. 화면에서 타이머가 0이 되는 순간과 서버가 실제로 회수하는 순간에 최대 30초 차이가 날 수 있다.
  • 그래서 타이머가 0이 되어도 클라이언트가 단정하지 않는다. 서버에 확인을 요청하고 410을 받은 뒤 이 모달을 띄운다. 아직 살아있으면 그대로 진행시킨다.
  • "결제는 진행되지 않았습니다"를 반드시 명시한다. 돈이 걸린 화면에서 침묵은 불안을 만든다.
  • 다시 선택으로 돌아가면 같은 좌석이 이미 남에게 갔을 수 있다. 좌석맵을 새로 받아온다.

E-03 결제 타임아웃 F-08 5단계 · F-10

토스페이먼츠 응답이 오지 않은 경우. 승인됐는지 안 됐는지 모르는 상태.

/holds/h_8f3a21/payment

결제 결과를 확인하고 있습니다

결제사 응답이 지연되고 있습니다. 결과를 확인하는 중입니다.
이 창을 닫거나 다시 결제하지 마세요.

확인 중… (3 / 10회)

주석 — 이 시스템에서 가장 어려운 화면

  • 승인 성공인지 실패인지 모르는 구간이다. 외부 결제와 내부 DB 사이에 분산 트랜잭션이 없어서 생기는 필연적 상태다.
  • 클라이언트는 같은 Idempotency-Key로 상태를 폴링한다. 새 결제 요청이 아니라 기존 요청의 결과 조회다. 이 구분이 무너지면 이중 결제가 난다.
  • "다시 결제" 버튼을 비활성으로 잠근다. 불안한 사용자가 누르는 것이 이중 결제의 가장 흔한 원인이다.
  • 폴링 상한(예: 10회) 도달 시 "예약 목록에서 확인해주세요"로 빠진다. 그 뒤 서버가 보상 취소(F-08 6단계)를 수행하면 선점이 반환된다.
  • 이 화면은 멱등성 검증의 대상이다 — 강제 타임아웃을 주입해 이중 결제가 없음을 확인하는 것이 비기능 요구다.
