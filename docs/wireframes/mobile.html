웹과 무엇이 다른가

웹과 기능이 완전히 같다. 키오스크 채널이 2026-09-04 철회되면서 비회원 예매도 함께 사라졌다.

다른 건 셋이다. ① 좌석 배치도가 가로로 안 들어간다 ② 앱이 백그라운드로 가면 SSE가 끊긴다 ③ 결제 중 앱을 벗어났다 돌아온다.

그래서 M-03과 E-04에 설계 무게를 뒀다. 나머지 화면은 웹과 구조가 같아 간략히 그렸다.

핵심 결정 — 가로 격자를 세로로 돌렸다

  • 웹은 진행방향이 가로라 한 호차가 좌우로 길게 놓인다. 375px에서는 그대로 못 넣는다.
  • 모바일은 진행방향을 위로 세우고 4열(A B · 통로 · C D) 고정, 세로 스크롤로 바꿨다. 좌석 폭 약 60px씩 4열 + 통로 = 여유 있게 들어간다.
  • 이러면 손가락이 자연스럽게 위아래로 움직인다. 가로 스크롤이나 핀치 확대는 좌석 선택처럼 정확도가 필요한 조작과 상극이다.

주석

  • 호차 이동을 세그먼트 컨트롤 + 좌우 화살표로 뒀다. 18호차를 탭으로 나열할 수 없으니 현재 호차 주변만 보이고 화살표로 넘긴다.
  • 선택 요약과 선점 버튼을 하단에 고정한다. 좌석 목록을 스크롤하는 동안에도 2 / 6과 금액이 항상 보여야 한다.
  • 실시간 배지를 내비게이션 바에 올렸다(F-16). 공간이 좁아 "실시간 연결됨" 대신 "실시간"으로 줄였고, 끊기면 빨강 + "재연결 중"으로 바뀐다.
  • 좌석 주소 체계는 미확정이다. 일련번호 방식으로 정해지면 호차 세그먼트가 사라지고 스크롤 하나로 단순해진다 — 모바일이 웹보다 이 결정에 훨씬 크게 영향받는다.
  • 격자는 4×15로 축약해 그렸다. 실제 배열은 시드 데이터를 따른다.

주석 — 앱을 벗어난다

  • 결제창(토스페이먼츠 SDK 또는 웹뷰)으로 가는 순간 앱이 백그라운드로 간다. 이때 SSE가 끊기고, 타이머 인터벌이 멈출 수 있고, OS가 앱을 죽일 수도 있다.
  • 따라서 결제 진입 직전에 상태를 반드시 서버에 남긴다. 복귀 후 화면 상태를 메모리에서 복원하려 하면 앱이 죽었을 때 아무것도 없다.
  • Idempotency-Key는 이 화면 진입 시 1회 생성하고 영속 저장한다(AsyncStorage 등). 웹은 메모리로 버텨도 되지만 모바일은 프로세스가 죽으면 키가 사라진다 — 그러면 복귀 후 재시도가 새 결제가 되어 이중 결제가 난다.
  • 복귀 시 순서 — ① 선점이 아직 유효한가 ② 결제가 이미 승인됐는가. ②를 먼저 확인하지 않으면 승인된 건을 만료로 오판한다.
  • 버튼은 클릭 즉시 비활성. 이중 제출은 UI와 서버 양쪽에서 막는다.

  • 이메일은 변경 불가. 소유 증명 수단이 없는데 변경을 허용하면 계정이 남의 것이 될 수 있다.
  • 비밀번호 변경도 범위 밖이다(F-23 철회). 재설정에 이어 변경까지 빠지면서 사용자가 비밀번호를 바꿀 수단이 전혀 없다. 의도된 축소이지 누락이 아니다.
  • 로그아웃(F-25)을 이 화면에 뒀다. Redis에서 Refresh를 삭제한다.
  • 회원 탈퇴는 범위 밖이다.

왜 이 화면이 필요한가

  • 모바일 앱은 홈 버튼 · 전화 수신 · 화면 잠금 · 다른 앱 전환으로 수시로 백그라운드에 간다. 그때 SSE 연결이 끊긴다. 웹 브라우저 탭보다 훨씬 자주, 훨씬 공격적으로 끊긴다.
  • 돌아왔을 때 화면에 남아 있는 좌석맵은 끊긴 시점의 낡은 상태다. 그걸 그대로 믿고 좌석을 누르면 선점이 계속 실패한다.
  • 그래서 복귀 시 좌석 선택을 잠시 비활성하고 재조회가 끝난 뒤 푼다. 낡은 화면으로 조작하게 두는 것보다 잠깐 막는 게 낫다.

순서처리

  • 3번이 중요하다. F-19는 Last-Event-ID로 놓친 이벤트를 받는 설계인데, 백그라운드가 길면 서버가 보관하는 이벤트 범위를 넘어간다. 그때는 재개가 아니라 전체 재조회로 떨어져야 한다. 재개가 실패했는데 성공한 척하면 좌석맵에 구멍이 남는다.
