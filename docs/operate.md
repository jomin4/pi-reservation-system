# 관측 · 로그 설계

확정일 2026-09-10

> **이 문서는 계약이 아니다.** [api.md](api.md)가 "클라이언트가 지켜야 할 것"이라면, 여기는 **"우리가 서버를 운영하는 방식"**이다. 로그 레벨을 바꿔도 아무도 깨지지 않는다.

## 문서 경계

| | `api.md` | **이 문서** |
|---|---|---|
| 독자 | API를 쓰는 쪽 | **서버를 운영하는 쪽** |
| 관측 관련 | `X-Request-Id` 헤더(§2) · `requestId` 에러 필드(§4) | 로그 · 메트릭 · 수집 · 경보 |
| 바뀌면 | **클라이언트가 깨진다** | 운영만 바뀐다 |

## §0 관측 원칙

이 시스템이 관측으로 **답해야 할 질문**부터 정한다. 답할 질문이 없는 데이터는 안 모은다.

| 질문 | 답하는 수단 |
|---|---|
| **이중 판매가 있었나** | **DB 대사 쿼리** — `data.md` §4.9 |
| 경합이 실제로 일어났나 | 메트릭 — 선점 시도 대비 패배율 |
| `lock_timeout` 200ms가 적절한가 | 메트릭 — 락 대기 분포 |
| 커밋이 클라에 몇 ms 만에 닿나 | 메트릭 — SSE 지연 |
| **돈이 새고 있나** | **로그 `ERROR`** — 미아 결제 |
| 이 사용자에게 무슨 일이 있었나 | 로그 — `requestId` 추적 |

> **가장 중요한 증거가 관측 도구 밖에 있다.** "초과 판매 0건"은 Grafana가 아니라 **SQL 한 방**이 증명한다. 메트릭은 *과정*을 보여주고, 대사 쿼리는 *결과*를 판정한다. 이 둘을 섞으면 안 된다.

### 0.1 안 하는 것

| 안 함 | 이유 |
|---|---|
| **분산 트레이싱 (OTel · Jaeger · Tempo)** | 모놀리스 1개 + PG + Redis + 토스. **스팬 트리가 4단**이라 트리를 볼 이유가 적다 |
| | **호스트가 8GB**다. PG · Redis · 앱 · Prometheus · Grafana · Loki로 이미 4.1GB — **백엔드를 하나 더 올릴 자리가 없다** |
| 대체 수단 | **`requestId` + 타이밍 필드** — `lockWaitMs` `txMs` `pgCallMs`를 로그 한 줄에 넣는다 |
| APM (Datadog · New Relic) | 폐쇄망 + SaaS. 애초에 못 나간다 |
| 사용자 행동 분석 | 시연 대상이 아니다 |

> **트레이싱을 안 넣는 대신 로그 한 줄이 두꺼워진다.** 선점 요청 하나의 로그에 "락을 몇 ms 기다렸고, 트랜잭션이 몇 ms였는지"가 필드로 들어간다. 스팬 트리로 볼 수 있는 걸 **평평한 필드로 대신 본다** — 계층이 얕아서 가능한 절충이다.

## §1 로그 레벨 정책

**이 절이 이 문서에서 가장 중요하다.**

### 1.1 원칙

> **`ERROR`는 사람이 개입해야 하는 것만.**

이 시스템은 `409`를 **정상적으로, 자주** 낸다. 경합이 곧 제품이기 때문이다. 그걸 `ERROR`로 찍으면 세 가지가 동시에 망가진다.

| 망가지는 것 | 결과 |
|---|---|
| 경보 | **정상 동작이 장애로 보고된다** |
| **응답시간** | **동기 로그 I/O가 응답 경로의 병목이 된다** |
| 진짜 에러 | 미아 결제 1건이 `409` 10만 건에 묻힌다 |

> **두 번째가 치명적이다.** 관측하려고 만든 로그가 관측 대상을 왜곡한다. 경합이 심할수록 로그가 많아지고, 로그가 많아질수록 응답이 느려지고, 느려질수록 경합이 더 심해진다 — **자기 강화 루프**다.

### 1.2 레벨이 뜻하는 것

레벨은 **심각도가 아니라 "누가 언제 봐야 하는가"**로 정의한다.

| 레벨 | 한 줄 정의 | **판별 질문** | 누가 보나 | 조치 시점 | 이 시스템의 대표 사례 |
|---|---|---|---|---|---|
| **`ERROR`** | **사람이 개입하지 않으면 복구되지 않는다** | *"자고 일어나도 저절로 안 풀리나?"* | **경보 → 사람** | **지금** | 미아 결제 · `500` · PG 연결 실패 |
| **`WARN`** | 지금은 동작하지만 **임계에 가까워졌거나 의심스럽다** | *"이게 계속 늘면 곤란한가?"* | 대시보드 · **추세** | **누적되면** | `SEAT_LOCK_TIMEOUT` · `429` · `202` |
| **`INFO`** | 정상 흐름 중 **나중에 되짚을 가치가 있는 사건** | *"사용자 문의가 오면 이게 필요한가?"* | 사후 추적 (`requestId`) | **없음** | `SEAT_ALREADY_HELD` · 선점 생성 · 예약 확정 |
| **`DEBUG`** | 개발자가 **재현할 때만** 필요 | *"운영에서 이걸 볼 일이 있나?"* | 개발자 (로컬) | 없음 | `400` 검증 실패 · `401` |
| ~~`TRACE`~~ | **쓰지 않는다** | — | — | — | — |

> **`TRACE`를 빼는 이유** — `DEBUG`와의 경계가 사람마다 달라 결국 아무 기준 없이 섞인다. 레벨이 5개면 판단이 5갈래로 갈리고, **판단이 갈리는 순간 레벨 정책은 없는 것과 같다.**

### 1.3 위에서 아래로 내려가며 판단한다

```
ERROR 인가?  → 사람이 지금 개입해야 하나?           아니오 ↓
WARN  인가?  → 늘어나면 곤란한가? 공격 신호인가?    아니오 ↓
INFO  인가?  → 문의 대응·사후 추적에 필요한가?      아니오 ↓
DEBUG
```

> **의도** — "얼마나 나쁜가"로 고르면 `409`처럼 **결과는 실패지만 시스템은 정상**인 사건에서 반드시 흔들린다. **"누가 언제 봐야 하나"로 물으면 답이 하나로 떨어진다** — `409`를 보고 새벽에 일어날 사람은 없다.

### 1.4 흔한 오용 — 이렇게 하지 않는다

| 오용 | 왜 틀렸나 |
|---|---|
| **HTTP `4xx` = `WARN`, `5xx` = `ERROR`** | **상태 코드는 클라이언트에게 하는 말이고, 레벨은 우리에게 하는 말이다.** `409`와 `500`은 같은 층위가 아니다 |
| 예외를 던졌으니 `ERROR` | 예외는 **제어 흐름**이다. `SeatConflictException`은 설계된 경로지 사고가 아니다 |
| 일단 `INFO`, 나중에 조정 | **조정되지 않는다.** 부하가 걸려 로그가 병목이 된 뒤에야 알게 된다 |
| `ERROR`에 `WARN`도 같이 | **경보가 울리기 시작하면 사람은 무시한다.** `ERROR` 목록이 짧아야 `ERROR`가 작동한다 |
| 스택트레이스를 `WARN`에도 | 스택트레이스는 **`ERROR` 전용.** `WARN`은 추세를 보는 것이지 원인을 캐는 게 아니다 |

> **첫 줄이 이 시스템에서 가장 하기 쉬운 실수다.** `@RestControllerAdvice` 한 곳에서 예외를 잡아 응답을 만들다 보면, **HTTP 상태 코드에 레벨을 맞추고 싶어진다.** 그 순간 `409`가 전부 `WARN`이 되고 경합이 곧 경고가 된다.

### 1.5 레벨 표

| 상황 | HTTP · `code` | 레벨 | 근거 |
|---|---|---|---|
| **경합 패배** | `409 SEAT_ALREADY_HELD` | **`INFO`** | **정상 결과다.** 이 시스템의 제품 그 자체 |
| **락 타임아웃** | `409 SEAT_LOCK_TIMEOUT` | **`WARN`** | **임계 신호** — 200ms가 부족하다는 뜻 |
| 선점 만료 | `410 HOLD_EXPIRED` | `INFO` | 시간이 지난 것 |
| 좌석 수 초과 | `400 SEAT_COUNT_EXCEEDED` | `DEBUG` | 클라가 미리 막았어야 |
| 검증 실패 | `400 VALIDATION_FAILED` | `DEBUG` | 클라 잘못 |
| 미인증 · 자격 불일치 | `401` | `DEBUG` | 일상 |
| 남의 자원 접근 | `403 *_NOT_OWNED` | **`WARN`** | **탐색 시도일 수 있다** |
| **시도 제한 발동** | `429 TOO_MANY_ATTEMPTS` | **`WARN`** | **공격 신호** |
| 결제 거절 | `402 PAYMENT_DECLINED` | `INFO` | **PG 판단.** 우리 잘못이 아니다 |
| 결제 미확정 | `202 PAYMENT_PENDING` | **`WARN`** | 보상 대상 후보 |
| 금액 불일치 | `400 PAYMENT_AMOUNT_MISMATCH` | **`WARN`** | **위변조 시도 가능성** |
| **미아 결제** | — (`payment.reservation_id IS NULL`) | **`ERROR`** | **돈이 걸렸다** |
| SSE 재개 실패 | `resume-failed` 이벤트 | `INFO` | 보관 범위를 벗어난 정상 경로 |
| 외부 PG 연결 실패 | `502` `504` | **`ERROR`** | 의존 장애 |
| 예상 못한 예외 | `500` | **`ERROR`** | |

### 1.6 `409` 두 종류를 다르게 찍는 이유

| | `SEAT_ALREADY_HELD` | `SEAT_LOCK_TIMEOUT` |
|---|---|---|
| 뜻 | **남이 먼저 가져갔다** | **판정조차 못 했다** |
| 레벨 | `INFO` | **`WARN`** |
| 늘어나면 | 인기 좌석 (정상) | **`lock_timeout`이 짧거나 트랜잭션이 길다** |
| 조치 | 없음 | **설계 재검토** |

> `api.md` §4에서 이 둘을 나눈 이유가 "사용자 행동이 반대라서"였다. **로그에서는 이유가 하나 더 붙는다** — 하나는 정상 분포이고, 하나는 시스템이 한계에 닿았다는 신호다. 같은 `409`지만 대시보드에서 완전히 다른 선으로 그려야 한다.

### 1.7 부하 상황 프로파일

| 프로파일 | 루트 레벨 | 접근자 |
|---|---|---|
| `local` | `DEBUG` | 동기 |
| `prod` | **`INFO`** | **비동기 (`AsyncAppender`)** |
| **`prod-measure`** | **`WARN`** | 비동기 · **큐 만차 시 폐기** |

```xml
<!-- prod: 큐가 차면 INFO 이하를 버린다. 응답을 막지 않는다 -->
<appender class="ch.qos.logback.classic.AsyncAppender">
  <queueSize>8192</queueSize>
  <discardingThreshold>20</discardingThreshold>  <!-- 20% 남으면 INFO 이하 폐기 -->
  <neverBlock>true</neverBlock>                  <!-- 절대 응답 스레드를 막지 않는다 -->
</appender>
```

> **`neverBlock=true`가 핵심이다.** 기본값(`false`)이면 큐가 찼을 때 **응답 스레드가 로그를 기다린다.** 관측 때문에 서비스가 느려지는 건 본말전도다. **로그는 유실돼도 되지만 응답은 아니다.**
>
> 측정용 프로파일을 따로 두는 이유도 같다. 성능을 재는 동안에는 **로그가 측정을 방해하면 안 된다.**

## §2 로그 구조 · 상관관계

### 2.1 형식 — 구조화 JSON

```json
{
  "ts": "2026-09-10T05:18:02.417Z",
  "level": "INFO",
  "logger": "seat.hold",
  "imageTag": "sha-abc1234",
  "requestId": "7f3a9c21",
  "memberId": 1042,
  "event": "HOLD_REJECTED",
  "tripId": 101,
  "seatCount": 6,
  "failedCount": 2,
  "reason": "SEAT_ALREADY_HELD",
  "lockWaitMs": 37,
  "txMs": 51
}
```

| 필드군 | 내용 | 비고 |
|---|---|---|
| 고정 | `ts` `level` `logger` | 전부 |
| **배포** | **`imageTag`** | **모든 로그에 고정.** 아래 참조 |
| **상관** | **`requestId`** · `memberId` | **MDC 자동 부착** |
| 사건 | `event` — `SCREAMING_SNAKE_CASE` | 검색 열쇠 |
| 도메인 | `tripId` `seatCount` `reason` … | 사건마다 다름 |
| **타이밍** | **`lockWaitMs` `txMs` `pgCallMs`** | **트레이싱 대체** |

> **`imageTag`가 로그와 배포를 잇는다.** 없으면 **"이 에러가 언제부터 나기 시작했나"**를 배포 이력과 대조할 방법이 없다. Loki에서 `imageTag`로 필터하면 **"이 배포 이후 발생한 에러"**가 즉시 갈리고, `deploy.md` §12의 롤백 판단이 **추측에서 관측으로** 바뀐다.
>
> 값은 컨테이너 환경변수(`IMAGE_TAG`)에서 읽어 **기동 시 한 번** 고정한다.

> **`message` 문자열이 없다.** 사람이 읽을 문장을 만들면 그걸 파싱하려는 정규식이 생기고, 문구를 바꾸는 순간 대시보드가 깨진다. **`event` 하나로 식별하고 나머지는 필드로 준다.**

### 2.2 상관관계 ID 전파

```
클라이언트 ──X-Request-Id: 7f3a…──▶ Cloudflare ──▶ 게이트웨이 ──▶ 앱
                                                                 │
                                          필터가 MDC에 넣는다 (없으면 생성)
                                                                 │
                              모든 로그에 자동 부착 · 응답 헤더 · 에러 본문에 에코
```

| 경로 | 상관 키 | 만드는 곳 |
|---|---|---|
| HTTP 요청 | **`requestId`** | `:adapter-web` 필터 |
| 스케줄러 실행 | **`jobRunId`** | `:adapter-scheduling` |
| SSE 연결 | **`connectionId`** | `:adapter-web` |
| Stream 소비 | **`eventId`** (Redis Stream ID) | `:adapter-cache` |

> **HTTP만 상관 키가 있으면 절반이 안 보인다.** 만료 회수는 스케줄러가 하고, SSE 전파는 Stream 소비 루프가 한다 — **좌석 상태를 바꾸는 5개 전이 중 하나(`TS-3`)는 HTTP 밖**이다(`api.md` §5.6). 각 진입점이 자기 상관 키를 만들어야 한다.

**SSE는 상관 키가 둘이다.** 연결은 오래 살고 이벤트는 계속 흐른다.

| | 수명 | 쓰임 |
|---|---|---|
| `connectionId` | 연결 전체 | "이 클라가 언제 붙고 언제 끊겼나" |
| `eventId` | 이벤트 1건 | "이 좌석 변경이 몇 ms 만에 닿았나" |

### 2.3 모듈별 로깅 책임

| 모듈 | 로깅 | 의존 |
|---|---|---|
| **`:domain`** | ❌ **금지** | 없음 (의존성 0 유지) |
| **`:application`** | ✅ 유스케이스 단위 | **SLF4J API만** |
| `:adapter-*` | ✅ 경계 진입·이탈 | SLF4J API |
| `:bootstrap` | — | **Logback 구현체는 여기만** |

> **SLF4J는 프레임워크가 아니라 파사드다.** 구현체를 `:bootstrap`에만 두면 `:application`은 여전히 Spring 의존 0이다.
>
> **`:domain`에서 로깅을 금지하는 이유**는 의존성 0 원칙 말고 하나 더 있다. 도메인 규칙은 **"6석 중 2석이 실패했다"는 사실을 반환**해야지 로그로 흘려보내면 안 된다. 로그를 찍고 싶어지는 순간, 그 정보가 반환값에 없다는 뜻이다.

**계층별로 무엇을 찍나**

| 계층 | 찍는 것 | 예 |
|---|---|---|
| `:adapter-web` | 요청 수신 · 응답 상태 · **HTTP 매핑 결과** | `HTTP_409` |
| `:application` | **유스케이스 결과 · 도메인 판정 이유** | `HOLD_REJECTED` `reason=SEAT_ALREADY_HELD` |
| `:adapter-persistence` | **락 대기 · 트랜잭션 시간** | `lockWaitMs=37` |
| `:adapter-payment` | 외부 호출 왕복 시간 · **마스킹된** 응답 | `pgCallMs=812` |

## §3 마스킹

### 3.1 화이트리스트

> **찍을 필드를 명시한다. 가릴 필드를 명시하지 않는다.**

| | **화이트리스트 (채택)** | 블랙리스트 |
|---|---|---|
| 방식 | 로깅할 필드를 코드에 나열 | 가릴 필드를 나열 |
| 새 필드 추가 시 | **안 찍힌다 (안전)** | **그대로 샌다** |
| 요청 본문 | **통째로 안 찍는다** | 찍고 일부를 가린다 |

> **블랙리스트는 빼먹으면 샌다.** DTO에 필드를 추가할 때마다 마스킹 목록을 기억해야 하는 구조는 언젠가 반드시 뚫린다. **요청 본문을 통째로 덤프하는 코드를 아예 안 만드는 것**이 유일하게 확실한 방법이다.

### 3.2 절대 로그에 넣지 않는 것

| 값 | 처리 |
|---|---|
| `password` · `passwordHash` | **로그 경로에 존재하지 않는다** |
| `Authorization` 헤더 | **필터에서 제거** |
| `accessToken` · `refreshToken` | 〃 |
| 요청 본문 전체 | **덤프 금지** |

### 3.3 부분 노출

| 값 | 형태 | 이유 |
|---|---|---|
| `email` | `jo***@gmail.com` | 문의 대응에 도메인이 필요 |
| `phone` | `010-****-1234` | 뒤 4자리로 대조 |
| `paymentKey` | `tviva202…` (앞 8자) | 토스 대시보드 대조 |
| `passengerName` | `조*민` | |
| `Idempotency-Key` | **전체** | 민감정보가 아니고, **이중 결제 추적의 열쇠** |
| `reservationNo` | **전체** | 〃 |

> **`Idempotency-Key`를 가리면 안 된다.** 이중 결제 사고를 추적할 유일한 실마리다. 마스킹은 목적이 아니라 수단이고, **가려서 잃는 게 지켜서 얻는 것보다 크면 안 가린다.**

## §4 메트릭

Micrometer → Prometheus. **접두사 `pi_`.**

### 4.1 좌석 경합 — 이 프로젝트의 주인공

| 메트릭 | 타입 | 라벨 | 답하는 질문 |
|---|---|---|---|
| `pi_hold_attempt_total` | Counter | `result` = `success`\|`conflict`\|`timeout` | **경합이 실제로 일어났나** |
| `pi_hold_seat_count` | Histogram | — | 몇 석씩 잡나 |
| **`pi_seat_lock_wait_seconds`** | **Histogram** | — | **200ms가 적절한가** |
| `pi_seat_tx_seconds` | Histogram | `usecase` | 트랜잭션이 길어지나 |
| `pi_hold_expired_total` | Counter | — | 스케줄러 회수량 |
| `pi_hold_to_confirm_seconds` | Histogram | — | 선점→확정 전환 시간 |

> **`pi_seat_lock_wait_seconds`의 p99가 200ms에 붙기 시작하면 `lock_timeout`을 올릴 게 아니라 트랜잭션을 줄여야 한다.** 타임아웃을 늘리면 실패가 줄어드는 대신 **모두가 더 오래 기다린다** — 처리량이 떨어진다.

### 4.2 SSE

| 메트릭 | 타입 | 답하는 질문 |
|---|---|---|
| `pi_sse_connections_active` | Gauge | 지금 몇 명이 보고 있나 |
| **`pi_sse_event_lag_seconds`** | **Histogram** | **커밋 → 클라 도달 (비기능 요구 1초)** |
| `pi_sse_resume_total` | Counter (`result`) | 재개가 성공하나 |
| `pi_sse_reconnect_total` | Counter | **재연결 폭주 감지** |
| `pi_stream_backlog` | Gauge | Stream 소비가 밀리나 |

> **`pi_sse_reconnect_total`이 `api.md` §6.6에 남긴 미해결 항목의 측정 도구다.** 서버 재시작 직후 이 값이 계단처럼 튀면 폭주가 실재한다는 뜻이고, 그때 대응하면 된다.

### 4.3 결제

| 메트릭 | 타입 | 라벨 |
|---|---|---|
| `pi_payment_duration_seconds` | Histogram | `outcome` = `approved`\|`declined`\|`timeout` |
| **`pi_payment_orphan_total`** | **Counter** | — |
| `pi_idempotency_replay_total` | Counter | — |

> **`pi_payment_orphan_total`은 0이어야 한다.** 승인은 됐는데 예약이 안 붙은 건수 — `ERROR` 로그와 이 카운터가 같은 사건을 가리킨다.

### 4.4 기본 제공 (Spring Boot Actuator)

| 영역 | 메트릭 |
|---|---|
| HTTP | `http_server_requests_seconds{status,uri}` |
| **커넥션 풀** | `hikaricp_connections_pending` — **락 대기와 함께 봐야 한다** |
| JVM | 힙 · GC · 스레드 |
| Redis | `lettuce_command_*` |
| **헬스체크** | **`/actuator/health`** — `db` · `redis` 컴포넌트 포함 |

**헬스체크 정의** — `deploy.md` §12 롤백 확인과 §7 경보가 같은 엔드포인트를 쓴다.

| 항목 | 값 |
|---|---|
| 경로 | `/actuator/health` |
| 노출 | **`net:app` 내부만** — 인터넷에 안 낸다 |
| `UP` 조건 | 앱 기동 + **PostgreSQL 연결 가능** |
| Redis | ⚠️ **`UP` 조건에서 뺀다** |

> ⚠️ **Redis를 헬스체크에 넣으면 안 된다.** `data.md` §6.7이 캐시·SSE·시도제한을 **fail-open**으로 정했다 — **Redis가 죽어도 예매는 된다.** 그런데 헬스체크가 `DOWN`이 되면 nginx가 앱을 빼버려 **fail-open 설계가 무의미해진다.**

> **`hikaricp_connections_pending`이 락 대기의 그림자다.** 트랜잭션이 락을 기다리는 동안 커넥션을 쥐고 있으므로, 락 경합이 심해지면 **커넥션 고갈이 먼저 터진다.** 두 그래프를 같은 패널에 겹쳐 둔다.

### 익스포터 4종

| 대상 | 도구 | 메모리 |
|---|---|---|
| 앱 · JVM | **Actuator** — 이미 있다 | 0 |
| 호스트 (CPU · RAM · 스왑 · 디스크) | **`node_exporter`** | ~30 MB |
| PostgreSQL | **`postgres_exporter`** | ~30 MB |
| Redis | **`redis_exporter`** | ~20 MB |
| ~~컨테이너별 사용량~~ | ~~cAdvisor~~ | ~~100 MB~~ |

> **cAdvisor는 넣지 않는다.** 컨테이너별 분해에 100MB를 내주기엔 8GB가 아깝다. **`docker stats`로 수동 확인**하고 필요해지면 그때 추가한다.

> **`node_exporter`는 경보에도 쓰인다** — §7의 백업 dead man's switch가 **textfile collector**를 쓴다.

| 구성 | 선택 | 메모리 |
|---|---|---|
| 로그 수집 | **Promtail** | ~50MB |
| 로그 저장 | **Loki** | ~450MB |
| 메트릭 | **Prometheus** | ~400MB |
| 시각화 | **Grafana** | ~200MB |
| **익스포터 3종** | node · postgres · redis | **~80MB** |
| ~~트레이싱~~ | ❌ 없음 (§0.1) | — |
| **합계** | | **≈ 1.18 GB** |

> ⚠️ **8GB 호스트에서 관측 스택이 예산의 1/4을 쓴다** (전체 4.43GB 중 1.18GB — `infra.md` §1.1). 넣을 수 있지만 **우선순위는 앱 2대 > Loki**다 — 둘 다 못 넣는 상황이 오면 **Loki를 먼저 뺀다.** 로그는 `docker compose logs`로 떨어지고, 메트릭이 §0에서 정한 주력이다.

### 왜 Loki인가 — 검색이 아니라 한 화면

| | 파일 + `logrotate` | **Loki** | ELK |
|---|---|---|---|
| 메모리 | 0 | ~450MB | **2GB+** |
| 컨테이너 여러 개 | **각각 `docker logs`** | **통합** | 통합 |
| Grafana | ❌ | **✅ 메트릭과 같은 대시보드** | 별도 Kibana |

> **Loki를 고르는 진짜 이유는 검색 성능이 아니다.** "락 대기가 튄 시점"(메트릭)과 "그때 무슨 로그가 찍혔나"를 **같은 화면에서 시간축을 맞춰 보는 것** — 그게 경합 분석의 전부다. ELK는 그걸 하려면 창을 두 개 띄워야 하고, 메모리는 4배를 쓴다.
>
> **호스트가 1대여도 컨테이너는 여러 개다.** 앱을 2대로 올리면 로그가 두 곳에서 나오므로 통합의 이유는 그대로 남는다.

| **DB 대사 결과** | **영구** — 문서에 기록 | **최종 증거** |

## §6 대시보드

### 6.1 계층으로 나눈다 — 4개

**표준 프레임을 그대로 쓴다.** 계층마다 관례로 정해진 축이 있다.

| # | 대시보드 | 축 | 답하는 질문 | 시점 |
|---|---|---|---|---|
| **1** | **인프라** | **USE** (Utilization · Saturation · Errors) | 호스트가 여유 있나 | ✅ 초반 |
| **2** | **백엔드 앱** | **Golden Signals** (Latency · Traffic · Errors · Saturation) | API가 정상 응답하나 | ✅ 초반 |
| **3** | **데이터** | 연결 · 캐시 · 락 | PG · Redis가 건강한가 | ✅ 초반 |
| 4 | **좌석 경합** | 프로젝트 전용 | **정확히 하나만 성공하나** | ⬜ 나중 |

> **1~3은 계층 대시보드, 4는 문제 대시보드다.** 앞의 셋은 **"시스템이 건강한가"**를 묻고 넷째는 **"이 프로젝트의 주장이 성립하나"**를 묻는다. 층위가 다르므로 섞지 않는다.

> **보는 순서가 `infra.md` §10의 병목 순서와 같다.** 1 → 2 → 3. **메모리가 1번 병목**이니 1번을 먼저 본다.

### 6.2 초반에는 직접 만들지 않는다

| 대시보드 | 출처 |
|---|---|
| 1 인프라 | **커뮤니티** — Node Exporter Full 계열 |
| 2 앱 | **커뮤니티** — JVM (Micrometer) 계열 |
| 3 데이터 | **커뮤니티** — PostgreSQL · Redis 공식 |
| **4 좌석 경합** | **직접 만든다** |

> **1~3에 시간을 쓸 곳이 아니다.** 가져다 쓰고 필요한 패널만 덧붙인다. **4번만 우리 것**이고 그게 이 프로젝트가 보여줄 것이다.
>
> ⚠️ **대시보드 ID는 세팅 시점에 확인할 것.** 번호와 호환 버전이 바뀐다.

### 6.3 대시보드 1 — 인프라

| 패널 | 비고 |
|---|---|
| CPU 사용률 | |
| **메모리 사용/여유 + 스왑** | ⚠️ **1번 병목.** 스왑이 0을 벗어나면 신호 |
| 디스크 사용률 · I/O | 10GB 미만이라 여유롭다 (`infra.md` §6) |
| 네트워크 in/out | |
| Load average | |

> **`infra.md` §10이 "메모리가 1번 병목"이라고 했으니 이 패널이 맨 위여야 한다.** 스왑이 시작되면 **락 대기와 커넥션 고갈이 따라오므로** 원인을 락으로 오진하기 쉽다.

### 6.4 대시보드 2 — 백엔드 앱

| 패널 | Golden Signal |
|---|---|
| **요청 수 (RPS)** | Traffic |
| **에러율 (`5xx`)** | Errors |
| **응답시간 p50 · p95 · p99** | Latency |
| **Hikari 커넥션 풀** (활성 / 대기 / **최대 10**) | Saturation |
| JVM 힙 + GC 시간 | Saturation |
| 스레드 수 | Saturation |

> ⚠️ **에러율에 `4xx`를 넣으면 안 된다.** `409`가 정상 결과라(§1) **4xx를 에러율에 넣으면 경합이 심할 때마다 대시보드가 빨개진다.** `5xx`만 센다.
>
> **`hikaricp_connections_pending`을 여기 둔다.** `infra.md` §10의 **2번 병목**이고, 락 대기(대시보드 4)의 그림자다.

### 6.5 대시보드 3 — 데이터

| 패널 | 비고 |
|---|---|
| PG 연결 수 (활성 / 유휴 / **최대 50**) | `infra.md` §3.2 |
| **PG 캐시 히트율** | 데이터가 100MB라 **99%+가 정상** |
| **PG 락 대기 · 데드락 수** | ⚠️ **데드락은 0이어야 한다** |
| PG 트랜잭션 (commit / rollback) | |
| Redis 메모리 사용 (**/256MB**) | `noeviction`이라 만차 = **쓰기 실패** |
| Redis 명령 처리량 | |

> **데드락 수가 0이 아니면 ADR-0002의 잠금 순서 결정이 지켜지지 않는 것이다.** `ORDER BY id`를 빠뜨린 코드가 어딘가 있다는 뜻 — **이 패널 하나가 그걸 잡는다.**

### 6.6 대시보드 4 — 좌석 경합 (나중)

**직접 만든다.** §4.1~§4.3의 `pi_*` 메트릭을 쓴다.

| 패널 | 메트릭 |
|---|---|
| 선점 결과 비율 | `pi_hold_attempt_total{result}` |
| **락 대기 p50 · p99** | **`pi_seat_lock_wait_seconds`** — 200ms 임계 |
| SSE 연결 수 · **전파 지연 p99** | `pi_sse_connections_active` · **`pi_sse_event_lag_seconds`** |
| 결제 왕복 · `outcome` 분포 | `pi_payment_duration_seconds` |
| **미아 결제** | **`pi_payment_orphan_total`** — 0이어야 한다 |

> **왜 나중인가** — 이 대시보드가 의미를 갖는 건 **경합이 실제로 일어날 때**다. 부하를 만드는 수단이 초기 범위 밖이므로(`CLAUDE.md` 미확정), **동작하는 시스템이 나온 뒤에 만든다.**

### 6.7 규칙

> **대시보드마다 "이걸 보고 무엇을 판단하나"를 한 줄로 적는다.**

그게 없으면 **패널만 계속 늘어난다.** 판단에 쓰이지 않는 패널은 지운다.

## §7 경보

### 7.1 목적 — 조용한 실패 탐지

> **경보의 유일한 실질 목적은 "내가 안 보고 있을 때 조용히 망가진 걸 알려주는 것"이다.**

| 상황 | 수단 |
|---|---|
| **보고 있을 때** | **대시보드로 충분** — 경보 불필요 |
| **안 보고 있을 때 조용히 망가지는 것** | **경보** |

사용자가 없는 포트폴리오라 "장애 대응"이 아니다. **이 기준으로 짜면 목록이 짧아진다.**

**판별 질문은 §1.2와 같다** — *"지금 사람이 개입해야 복구되나"*. **로그 레벨과 경보 심각도가 같은 축을 쓴다.**

### 7.2 채널을 더 나누지 않는다

| | |
|---|---|
| ❌ | `#alert-critical` · `#alert-warning` 분리 → **관리 대상이 늘어난다** |
| ✅ | **`#alert` 하나 + mention 유무** |

| 심각도 | Discord |
|---|---|
| **critical** | **`@here`** + 빨강 → **폰 푸시** |
| warning | mention 없음 + 노랑 |
| resolved | 초록 · **critical만** |

> **`resolved`를 critical에만 켠다.** 전부 켜면 알림이 2배가 된다. **복구를 확인해야 하는 건 critical뿐**이다.

### 7.3 초반 경보 — critical 10개

**대시보드 계층과 정렬한다.**

| 8 | 도메인 | **미아 결제** | 0 초과 | **돈.** 사용자가 신고하지 않는다 |
| 9 | 도메인 | **`ERROR` 로그** | 0 초과 | 정의상 사람이 필요 (§1.2) |
| **10** | 운영 | **백업 실패** | §7.4 | ⚠️ **가장 전형적인 조용한 실패** |

### 7.4 ⚠️ 백업 — dead man's switch

ADR-0006이 일 1회 백업을 정했는데, **cron이 조용히 실패하면 며칠 뒤에 안다.**

**"실패했을 때 알리기"는 안 된다** — cron 자체가 안 돌면 실패 신호도 안 온다.

| 단계 | 내용 |
|---|---|
| 1 | 백업 **성공 시** 타임스탬프를 파일에 쓴다 |
| 2 | `node_exporter` **textfile collector**가 메트릭으로 노출 |
| 3 | **36시간 넘게 갱신이 없으면** 경보 |

```bash
# 백업 스크립트 마지막 줄
echo "pi_backup_last_success_timestamp $(date +%s)" > /var/lib/node_exporter/textfile/backup.prom
```

```yaml
- alert: BackupStale
  expr: time() - pi_backup_last_success_timestamp > 129600   # 36h
  labels: { severity: critical }
  annotations:
    summary: "백업이 36시간 넘게 성공하지 않았다"
    action: "cron · age 키 · R2 자격증명을 순서대로 확인 (ADR-0006)"
```

> **성공을 기록하고 부재를 경보한다.** cron이 죽었는지, 스크립트가 깨졌는지, R2가 거부했는지 **원인과 무관하게** 잡힌다. **조용한 실패를 잡는 정석**이다.
>
> **36시간인 이유** — 일 1회니 24시간이 정상 간격이다. 24로 잡으면 **실행 시각이 조금 밀려도 울린다.**

### 7.5 warning은 초반에 안 건다

| 항목 | 초반 |
|---|---|
| 메모리 여유 · CPU · 디스크 | **대시보드 1로만** |
| 응답시간 p99 · Hikari pending · JVM 힙 | **대시보드 2로만** |
| PG 연결 수 · 캐시 히트율 | **대시보드 3으로만** |
| 락 대기 p99 · SSE 지연 · `429` 급증 | **대시보드 4로만** (나중) |
| **Redis 다운** | **대시보드로만** |

> **Redis 다운이 경보가 아닌 게 `data.md` §6.7과 일치한다.** 캐시·SSE·시도제한은 **fail-open**이라 **Redis가 죽어도 예매는 된다** — 새벽에 깨울 일이 아니다. (`refresh` 토큰만 fail-closed라 재로그인이 막히는데, 그건 대시보드에서 보인다.)

### 7.6 ⚠️ 대사 쿼리는 경보가 아니다

| | |
|---|---|
| 초안 | "대사 쿼리 결과가 0행이 아니면 즉시 경보" |
| **문제** | 그 쿼리를 **누가 언제 돌리나.** 상시 실행하면 48만 행을 계속 훑는다 |
| **결정** | **경보에서 뺀다.** 배포 후 · 복구 리허설 시 **수동 실행** |

> **"0이어야 하는 것"이 경보 대상이 되려면 자동으로 측정돼야 한다.** 대사 쿼리(`data.md` §4.9)는 그게 아니다 — **검증 절차**로 남기고, 실시간 신호는 **미아 결제(8번)와 데드락(6번)**이 대신한다.

### 7.7 경보를 걸지 않는 것

| 안 걸음 | 이유 |
|---|---|
| **`409` 증가** | **정상이다.** 경합이 곧 제품 (§1) |
| `402` 결제 거절 | PG 판단, 우리 문제 아님 |
| `401` `400` | 클라 잘못 |
| SSE 재연결 | 네트워크는 원래 끊긴다 |
| **CI 실패** | `#ci` 채널 — 운영 경보가 아니다 (`deploy.md` §11) |

> **경보 목록이 짧아야 경보가 작동한다.** 울리는 게 많아지면 사람이 무시하기 시작하고, **그때부터 경보 시스템은 없는 것과 같다.** `409`에 경보를 걸었다면 첫날에 이미 꺼버렸을 것이다.

### 7.8 소음 억제 4장치

| 장치 | 값 | 효과 |
|---|---|---|
| **`for:`** | 2~5분 | **순간 스파이크에 안 울린다** |
| `group_by` | `[severity, layer]` | 같은 계층 경보를 **한 메시지로** |
| `repeat_interval` | **4시간** | 해결 안 되면 4시간마다 (매분 아님) |
| **`inhibit_rules`** | 호스트 다운 시 하위 억제 | **원인 하나에 알림 하나** |

> **`inhibit_rules`가 없으면 호스트 하나 죽을 때 알림이 5개 온다.** 호스트가 죽으면 앱·PG·Redis도 죽으니 증상마다 울린다 — **그게 경보를 무시하게 만드는 첫 경험**이다.

### 7.9 전송 — Discord 웹훅

| 항목 | 값 |
|---|---|
| 방식 | **Alertmanager → Discord 웹훅 URL** |
| 웹훅 | `DISCORD_WEBHOOK_ALERT` — **호스트** `.env` (`deploy.md` §4) |
| 아웃바운드 | **`discord.com`** — `tinyproxy` 화이트리스트 3번째 |

> ⚠️ **Alertmanager 버전을 확인할 것.** Discord 웹훅 리시버(`discord_configs`)는 최신 버전에 있다. 없으면 `webhook_configs` + 변환 브리지가 필요하고 **컨테이너가 하나 늘어난다**(메모리 +).

### 7.10 메시지 형식

`deploy.md` §11.3과 같은 골격을 쓰되 필드가 다르다.

| 요소 | 규약 |
|---|---|
| 제목 | **`[계층] 경보명`** — `[데이터] 데드락 발생` |
| 색 | critical `#EF4444` · warning `#F59E0B` · resolved `#22C55E` |
| 필드 1 | 심각도 |
| 필드 2 | **현재값 / 임계값** |
| 필드 3 | 지속 시간 |
| 필드 4 | **대시보드 링크** |
| **설명** | ⚠️ **무엇을 해야 하나 — 한 줄** |

```
[데이터] 데드락 발생                          critical
현재값: 3건 / 임계 0        지속: 방금
조치: ORDER BY id 누락 코드를 찾는다 (ADR-0002)
링크: grafana.jomin4.cloud/d/data
```

> **"조치" 한 줄이 경보의 절반이다.** 없으면 받고도 뭘 할지 모른다. Alertmanager `annotations`에 **문서 참조까지** 넣는다 — **근거가 전부 문서에 있으니 그걸 가리키면 된다.**
